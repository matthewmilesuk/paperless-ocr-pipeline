# Dependency pinning via pip-tools — 2026-07-30

## Background

Following the [venv realignment](2026-07-30-venv-realignment.md) earlier
today, `requirements.txt` was found to use loose `>=` ranges with no upper
bound on almost every package — the same pattern that let Django silently
drift from 5.x (intended) to 4.2 (what local dev was actually running).
Several other packages had already drifted across major versions
unnoticed under their loose ranges (e.g. `redis` 5→8, `watchdog` 4→6,
`google-cloud-documentai` 2→3).

## Approach: pip-tools, `requirements.in` → `requirements.txt`

- `requirements.in` now states intent: exact pins for everything except
  `Pillow` (`>=12.3,<13.0`) and `gunicorn` (`>=26.0,<27.0`), which are
  capped-but-not-exact so patch/minor security fixes can land without a
  manual bump. Rationale: both are exposed to untrusted input (image
  parsing, network-facing WSGI server), so the risk of missing a security
  release outweighs the risk of an unplanned minor-version change.
- `requirements.txt` is compiled from `requirements.in` via
  `pip-compile requirements.in -o requirements.txt` and is now the fully
  pinned, transitively-locked file the Dockerfile and local venv both
  install from. It is autogenerated — do not hand-edit it.

## Gotcha hit during this work

`pip-compile` (pip-tools 7.6.0, the latest release at time of writing)
fails under pip 26.2 with:

```
TypeError: RequirementCommand.make_requirement_preparer() missing 1
required keyword-only argument: 'allow_editables'
```

pip-tools reaches into pip's internal (non-public) API, which changed in
a recent pip release. Worked around by downgrading pip inside the venv
used to run the compile: `pip install "pip==24.3.1"`. This only affects
the tool used to *run* `pip-compile` — it has no effect on the pinned
versions in `requirements.txt` or what gets installed from it. If
`pip-compile` breaks again in the future, check whether this is still the
cause before assuming something else is wrong.

## Versions confirmed (compiled, and installed via `requirements.txt`)

Matches the versions verified in the venv-realignment run earlier today —
no version changed as a result of pinning; this only removed the
looseness in how they're specified. Confirmed via
`pip list --format=freeze` before and after compiling: identical, aside
from PEP 503 name-casing normalization (e.g. `Django` → `django`) and the
compile-only tooling (`pip`, `pip-tools`, `build`, `pyproject_hooks`)
which are not project dependencies.

Pinning via pip-tools introduced no behavioral change — `check`,
`makemigrations --check --dry-run`, and `test` all match the prior
verified run. Local venv and container now both install from the same
fully-pinned `requirements.txt`, generated from `requirements.in`.
